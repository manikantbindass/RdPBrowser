# Desktop operation and acceptance

Build the backend and desktop from the same branch. The desktop uses `/api/v1/auth/status` for session validation and batches of URL decisions. The backend retains its existing source-address and country restrictions. Polls leave the idle timestamp unchanged. Install the backend update before distributing this desktop build.

## Browser controls

The address bar accepts HTTP(S) addresses without embedded credentials, or sends search text to Google. Rust creates each content WebView. Native navigation callbacks authorize top-level destination URLs through the backend and preserve the browser's request method. Popups are canceled and their addresses are offered in the address bar for review. Each policy callback can block the UI thread for up to two seconds. Same-document changes, subresources, service workers and network traffic remain subject to the engine and OS. Application CSP governs the bundled shell. Remote WebViews have no capability grant, and privileged browser IPC also checks the caller label. OS inspection, screenshots and traffic bypass remain possible.

The policy monitor checks open content every 15 seconds and closes it on denial or service failure. Session refresh also closes existing content so it can reopen under the new credentials. Moving or resizing the main window closes content to avoid stale overlay geometry. Reopen the page from its tab. The WebViews request ephemeral browsing profiles. Verify cookies, overlays, popups and download behavior on each supported WebView engine before deploying.

The app stores bounded, versioned appearance, tabs, history and bookmarks in app-origin storage scoped to the authenticated organization and user. URLs are validated and saved without query strings or fragments. Paths may still contain sensitive information. Storage relies on OS profile permissions. Restored pages require an explicit open and fresh policy authorization. Passwords, access and refresh tokens, and device private keys stay in memory. The new browser shell supersedes the legacy dashboard and its experimental SSH and Laila UI paths. Enterprise OIDC browser handoff remains future work.

The Devices panel registers a device, enrolls a non-exportable P-256 WebCrypto key, and signs a backend challenge. Keys live for the running session. Restart requires a new enrollment. Administrative posture approval and hardware attestation are separate. Use Ctrl/Command+L, T, W and Tab from the main shell for address focus, tab creation, closing and switching. Native content forwards supported shortcuts to the shell. The shell offers light and dark appearance and reduced-motion support.

## Downloads and networking

Automatic WebView downloads are denied. The Downloads panel offers explicit saving of direct HTTPS `text/plain` responses of up to 5 MiB into the application-local `downloads` directory. The downloader rejects redirects, non-UTF-8 content and unsafe control characters, uses generated `.txt` filenames with exclusive creation, and sends neither page cookies nor access tokens to the download host. App-local files can still contain untrusted text. Authenticated website downloads, executable files, malware scanning and user-selected export destinations are outside this restricted path.

Network status reports the API source-address gate and optional local WireGuard peer activity. To require a recent handshake, build with `REMOTESHIELD_WG_EXECUTABLE` pointing to the operator-installed absolute `wg` executable. Set `REMOTESHIELD_WG_INTERFACE` and `REMOTESHIELD_WG_PEER` to the interface and peer public key at runtime. A failed probe blocks new content and downloads, and the policy monitor closes open content. A recent handshake is evidence of peer activity. The operator remains responsible for OS routes, DNS, IPv6 and the kill switch. No WireGuard configuration, privilege elevation or firewall changes are performed by the desktop.

## Packages and updates

- Windows MSI/NSIS targets use WebView2. Build with MSVC and the Windows SDK. Test the installed artifact under the intended user account and enterprise runtime policy.
- macOS DMG uses WKWebView. Build on macOS with Xcode tooling, and sign/notarize for distribution. An unsigned development build and a notarized installed app have different acceptance requirements.
- Linux deb/AppImage uses WebKitGTK 4.1 and desktop GUI libraries. Build with the corresponding development packages. Use the deb package manager for deb upgrades. Validate the AppImage on target distributions.

Build releases with matching HTTPS `VITE_SERVER_URL` and `REMOTESHIELD_SERVER` values. Without updater provisioning, Updates shows published release metadata only. To enable installation in release builds, embed `REMOTESHIELD_UPDATE_URL` and `REMOTESHIELD_UPDATE_PUBKEY` at build time. The feed must be HTTPS, carry platform-specific artifacts, and have Tauri-compatible signatures with a signed version matching the advertised release. Generate updater artifacts using a private release build configuration with `bundle.createUpdaterArtifacts` and trusted CI signing secrets. Keep the private key out of source, artifacts and logs. Installation requires an explicit click and passes through Tauri package and version-signature verification. Verify upgrade, wrong key, mismatched version, rollback and installer behavior with disposable signing credentials before enabling a production feed. [Tauri updater documentation](https://v2.tauri.app/plugin/updater/)

## Verification

Run `npm test --prefix desktop`, `npm run build --prefix desktop`, `cargo fmt --manifest-path desktop/src-tauri/Cargo.toml -- --check`, `cargo test --locked --manifest-path desktop/src-tauri/Cargo.toml`, and strict Clippy. The desktop checks workflow runs those checks on Windows, macOS and Linux. The backend architecture workflow covers the authenticated status contract and real PostgreSQL. On Windows, `node scripts/test-local-postgres.mjs --desktop-fixture` starts the disposable fixture. Use the generated credentials in the ignored fixture file and stop the backend by creating `.local-tests/desktop-stop`. The fixture requires loopback ports 3001 (API) and 3002 (test site) and the documented portable PostgreSQL prerequisites. Fixture markers can change the disposable URL policy or revoke its sessions. Never enable remote debugging on a distributed build.
