# Phase 04 database and API upgrade

This is a reviewed-development upgrade, not a production deployment approval. Back up the database and verify restoration in a disposable environment first. Keep the previous artifact/configuration and migration history. Do not edit `001_initial.sql`, drop volumes or replay the historical `schema.sql` snapshot.

## Database roles and deployment order

1. Stop application writers for the upgrade window. Migration `002_tenants.sql` takes table locks, adopts all existing records into `00000000-0000-4000-8000-000000000001` and adds tenant foreign keys/indexes/RLS in one transaction. Large databases need a measured maintenance window. Invalid legacy references or unexpected custom constraints fail the transaction; investigate without disabling constraints.
2. Generate a distinct random hex password of at least 32 characters for `remoteshield_app`. Keep it in the deployment secret store. The runtime role must be new/dedicated, must not own application tables or belong to privileged roles, and must have no superuser/BYPASSRLS/CREATE ROLE privileges. Runtime startup rejects superuser, BYPASSRLS and table-owner credentials. Migration credentials remain privileged and must not reach the runtime container.
3. Existing host configurations: preserve the previous owner URL as `MIGRATION_DATABASE_URL`; change `DATABASE_URL` to the same host/database using user `remoteshield_app` and the new password. Set `DB_RUNTIME_PASSWORD` privately to that same runtime password **only for the operator migration process**. `npm run migrate --prefix backend` uses the migration URL, verifies/applies checksums, then provisions the restricted role. Remove owner/provisioning secrets from the service process environment. Each later migration requires reapplying reviewed runtime grants.
4. Existing Compose configurations: add `DB_RUNTIME_PASS` to ignored `docker/.env`, distinct from `DB_PASS`. Compose requires it; missing configuration fails explicitly. The one-shot migrator receives the owner URL and provisions `remoteshield_app`; backend receives only the restricted URL and an empty provisioning variable. Fresh `node scripts/setup-dev.mjs` creates these settings without printing secrets or overwriting existing files. `docker compose --env-file docker/.env -f docker/docker-compose.yml -f docker/compose.dev.yml up -d --build --wait` runs local migration before backend startup. Production uses the base Compose file, real TLS, configured source filtering and reviewed secret injection.
5. Verify `/ready`, login, tenant lists and revocation with the upgraded artifact. Forced RLS applies even to the table owner, but PostgreSQL superusers and BYPASSRLS roles remain trusted infrastructure. RLS tenant context is transaction-local; pooled connections cannot retain another request's context. Application code must enter `withTenant` before any tenant query. Organization claims come from verified server-signed tokens, never an HTTP tenant header.

`backend/.env` generated for host development includes owner credentials so the explicit CLI can run; do not mount that file into a production service. Use separate environment files/secret scopes there. Do not print expanded Compose configuration, DB URLs or SQL containing passwords into CI logs.

## Organization/admin provisioning

Organization creation and initial administrator promotion are operator operations. With reviewed migration credentials, parameterize `INSERT INTO organizations(id,name) VALUES($1,$2)`. In an operator transaction set `SELECT set_config('app.organization_id',$1,true)` to the new UUID, insert a user with a bcrypt cost-12 password hash and the same explicit `organization_id`, then promote that organization user to `admin`. Do not place plaintext passwords in SQL history. Existing default-organization admins retain their role. There is no default password and `superadmin` has no cross-organization API privilege.

An authenticated tenant admin registers ordinary users through `POST /api/v1/users`; role/organization fields are rejected. Login accepts optional `organizationId`; omission selects the legacy organization. Public `/auth/register` creates only ordinary default-organization users. `REGISTRATION_ENABLED` defaults false in production and true in development/test; Compose explicitly defaults false. Enable only deliberately. Device registration is self-enrollment of a client-reported external ID/platform, not attestation or WireGuard key provisioning. Revoked registry entries and their sessions cannot be revived by registration.

## Client compatibility and intentional tightening

`/api` aliases remain, as do legacy response keys. New fields are additive. Login/register/refresh return persisted access sessions and refresh credentials; refresh is single-use and invalidates the replaced access token. Clients must replace both tokens atomically. Pre-upgrade access tokens remain valid in the legacy organization until expiry/revocation, using the current database role/account state. Pre-upgrade stateless refresh credentials require login. Logout now requires a valid authenticated access session; a malformed/stale token returns 401. Refresh needs a live, unlocked account and active, unrevoked session; an expired access JWT can still refresh before the stored refresh expiry.

Passwords at new registration are at most 72 UTF-8 bytes to prevent bcrypt truncation; existing password hashes are not rewritten. Duplicate names/emails are unique per organization. Admin force-logout accepts exactly one of userId/sessionId. IDs and booleans are strictly typed. List endpoints default to 50 rows, maximum 100, page maximum 10000; clients that assumed unlimited lists must paginate. Legacy response wrapper names are retained. Unknown/invisible tenant resources return 404, never global identifiers or counts.

Policy patterns are case-insensitive literals with `*` wildcard, without regex interpretation. HTTP(S) only; URL credentials are rejected. Active deny rules win; each nonempty allow group must match. `/proxy/check`, `/proxy/navigate` and `/policies/evaluate` share decisions. More than 100 active policies or 1000 legacy rules per list fails closed with 503 until the operator reduces policy capacity. Policy updates require the previous revision and return 409 on stale writes. These changes close legacy parity/protocol defects; they do not enforce client redirects, subresources or native traffic.

Client events reject arbitrary metadata (including secrets), require UUID idempotency keys, enforce a seven-day/five-minute timestamp window and label reports untrusted. Repeated user/clientEventId uses first-write-wins. Realtime admin events retain names but use isolated tenant rooms internally, revalidate before sensitive delivery, and force-logout revokes the database session. The existing empty snapshot map is not a durable live session inventory; use REST sessions. No durable notification-delivery guarantee is introduced.

## Operations and rollback

IP/auth rate limits use process-local memory; one backend process is the supported enforcement scope. Configure trusted proxies exactly. Multi-replica/global quotas, account-specific adaptive lockouts and durable distributed abuse controls are future requirements; no Redis/broker is introduced. Health/readiness probes bypass quotas, not database/role verification. Node request/header/keepalive deadlines are 15/10/5 seconds; shutdown withdraws readiness, closes realtime/HTTP, forces remaining HTTP connections after five seconds, and drains PostgreSQL queries (15-second statement timeout). Compose allows 30 seconds before kill. SIGINT/SIGTERM handlers share an idempotent stop promise.

Canonical audit rows are written in the mutation transaction. `audit.attempt` stdout means an attempt, not a committed mutation; `http.completed` gives response outcome. Neither contains request bodies/headers or raw tokens. Navigation logs omit query/fragment/userinfo and do not assert VPN verification when VPN_REQUIRED=false. Path segments/client identifiers can still contain sensitive business data: apply access control, retention and operator log redaction policies. Database administrators can still alter audit records; external immutable retention is not implemented.

There is no destructive down migration. Restoring the old application against this schema is unsafe because old global queries, conflict targets and role assumptions differ. Recovery uses the previous application plus a verified pre-upgrade database restore in a controlled window, with explicit treatment of post-upgrade writes; prefer a forward repair. Never disable RLS, grant BYPASSRLS or drop the volume to make readiness pass.
