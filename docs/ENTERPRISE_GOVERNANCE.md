# Enterprise integrations and governance

Phase 11 extends the existing control plane with OIDC setup and activation, SCIM 2.0 directory provisioning, group-based URL policies, independent access reviews and evidence exports. These controls support an organization's evidence collection and review procedures for SOC 2 readiness. Certification and control effectiveness require the organization's own operating evidence and an independent examination.

## Upgrade and administration

Apply checksummed migrations through `006_enterprise_governance.sql` with the separate migration role, then renew the restricted runtime grants. Back up the database and verify restoration first. Schedule the table locks and reapply the grants before starting the new backend. Keep both the admin assets and backend at the same revision. The migration preserves local users, existing identity links, sessions, alerts and organization/user policy assignments. An old backend rejects a newer migration history. Use a forward repair or restore the verified pre-upgrade backup if rollback is required. [Database roles and deployment](MIGRATION_PHASE04.md)

Tenant administrators can read integration metadata, manage URL policy assignments, review access and export scoped evidence. Only tenant superadmins can control provider activation, directory state, provisioning credentials and group-to-admin mappings. Use a second administrator to review the first administrator's access. Provisioning credentials have a separate scope from console or client sessions.

## Configure Okta or Microsoft Entra ID

Start with [credential-free examples](../backend/oidc.providers.enterprise.example.json). Create a confidential web application with authorization code grant, S256 PKCE, RS256 ID tokens and `client_secret_post`, then register the exact HTTPS callback. Store provider configuration in a private read-only `OIDC_PROVIDERS_FILE`. Inject the named client-secret environment variable and a distinct 32-byte hexadecimal `OIDC_STATE_KEY`. Keep the browser console on the same origin as the configured callback and include that HTTPS origin in `CORS_ORIGINS`.

| Provider | Issuer boundary | Identity linkage |
|---|---|---|
| Okta | Use the exact Okta organization issuer or authorization server issuer and its registered Web app. Verify discovery and claims against that specific issuer. | Link the signed `sub` explicitly. Automated linking can use `sub` only when a verified SCIM mapping supplies that same stable, app-specific subject as `externalId`. |
| Microsoft Entra ID | Use a single-tenant app registration and an exact workforce `https://login.microsoftonline.com/<tenant-uuid>/v2.0` issuer. | Link the signed `sub` explicitly or opt into `oid`. This automatically links a SCIM-owned account only when its `externalId` matches signed `oid` and signed `tid` matches the configured issuer tenant. |

The Entra example uses the workforce cloud. Multi-tenant authorities, consumer aliases and sovereign-cloud `oid` linking require separate configuration work and acceptance. Provider claims never grant a local role directly. Email, display name and group-name matching do not establish identity. Keep `provisioningSubjectClaim` at `none` until the specific provider-to-directory mapping is verified. The SCIM bearer can then control the identity and group membership of accounts in that directory, so keep that credential in the provider's secret store and restrict group administration in the IdP. [Microsoft OIDC protocol](https://learn.microsoft.com/en-us/entra/identity-platform/v2-protocols-oidc) · [Okta OIDC reference](https://developer.okta.com/docs/api/openapi/okta-oauth/guides/overview/)

1. Sign into the console using an independent, working superadmin account. Open Integrations → SSO providers and select Validate. The check uses the configured discovery endpoint and inspects exact issuer, HTTPS endpoints, authorization code, RS256, S256 and client auth method. It does not exchange a code or authenticate the supplied client secret. Discovery failure leaves the current state intact.
2. Enable a validated provider within 24 hours. New examples require explicit activation. Earlier configured providers retain their pre-upgrade behavior until managed through this workflow. Validation does not disrupt a matching active provider. Configuration changes on a managed provider require validation and activation again. Disablement revokes the provider's sessions and erases pending console grants. Legacy untagged sessions are revoked by matching their identity links. Leave a separately validated recovery administrator before tightening access policy.
3. Link a preexisting local account with `POST /api/v1/admin/identity-links` using the verified issuer subject, or provision a directory-owned account with an explicitly enabled subject binding. A directory owns only the accounts it created. Unlinking a directory account locks it to prevent relinking until an administrator explicitly unlocks it.
4. Open `/admin/`, expand Enterprise SSO and enter the configured provider ID. The normal browser authorization flow seals transaction context, binds state/nonce/PKCE and validates the signed ID token. A successful console callback sets a one-use HTTPS cookie and redirects to the console. The console exchanges it on the same origin within 60 seconds. Application tokens stay in tab memory. The legacy API callback keeps its JSON response for existing integrations. The IdP redirects the user's browser back to the control plane, so that browser still needs its configured network access.
5. Test a user and a separately linked administrator on the real tenant. Confirm claims, session issue/refresh, sign-out, failed token and MFA behavior. Use provider Conditional Access or sign-on policy and verify which `acr`/`amr` claims actually appear before setting RemoteShield MFA requirements. Empty claim arrays never assert MFA, and a particular Conditional Access setting does not establish an app-visible claim. Inspect only redacted claim metadata. [Identity and access operations](IDENTITY_AND_ACCESS.md)

Provider setup examples and simulated HTTPS discovery/token/JWKS fixtures exercise standards behavior. Live Okta and Entra tenant compatibility, MFA claim behavior and production secret rotation still require deployment acceptance. Secure callback logs should exclude URL query strings and cookies. The reference control Nginx logs `$uri` instead of `$request_uri` and scopes OIDC error logging. Apply equivalent policies on external proxies and observability services.

## Provision, map and deprovision

SCIM is disabled by default. On an approved production deployment, present `https://<scim-host>/scim/v2/<organization-uuid>` from a dedicated HTTPS ingress and set `SCIM_PUBLIC_BASE_URL=https://<scim-host>/scim/v2`. Only explicitly trusted proxies may assert the forwarding headers. The optional [Compose override](../docker/compose.scim.yml) uses a separate bind address and certificates, sets the private proxy address, and exposes only `/scim/v2/`. Configure `SCIM_DOMAIN`, `SCIM_BIND_IPV4` and `SCIM_CERTS_DIRECTORY` in private deployment settings, including a matching DNS record, TLS certification and scoped firewall allowance. Combine it with the production base, apply migration/grants first, then use the normal reviewed Compose deployment sequence. The existing VPN-bound control edge stays private. For disposable development, enable `SCIM_ENABLED=true` with the loopback dev override. Direct production plain HTTP requests are rejected. The provisioning limiter defaults to 200 requests per source per minute on one backend process.

1. In Integrations add a directory. Optionally associate it with an OIDC provider. Enable subject linking only if the verified IdP subject and SCIM `externalId` are the intended immutable match.
2. Issue an expiring credential and enter the one-time value in the IdP's provisioning secret field. The app stores only a hash, credential ID, scope and dates. Test the connection and confirm that an application JWT and an unrelated directory credential are refused.
3. In Okta configure SCIM 2.0 bearer authentication, supported user attributes, create/update/deactivate and Push Groups as needed. In Entra, use an enterprise app's automatic provisioning with the tenant URL and secret token. Scope synchronization to the assigned pilot users/groups, choose `userName` or an immutable `externalId` for matching, and disable mappings for unsupported fields. For Entra `oid` linking, map the originating user's object ID to lowercase SCIM `externalId`. [Okta SCIM request shapes](https://developer.okta.com/docs/api/openapi/okta-scim/guides/scim-20) · [Microsoft Entra provisioning setup and request shapes](https://learn.microsoft.com/en-us/entra/identity/app-provisioning/use-scim-to-provision-users-and-groups)
4. Provision a known test user and group, validate the returned IDs, then add and remove a member. In Integrations, a superadmin can explicitly map a group to `admin`. The default role is `user`. A mapped group delegates the ability to grant `admin` to that directory's membership owner. No mapping can create `superadmin` or adopt a local account. Select Directory groups in URL policies to apply policies to matching direct members. Organization and user scopes and policy history remain available. Deny rules retain precedence, and nonempty allow groups must each match.
5. Test `active=false` and DELETE. Deactivation revokes all application sessions and refresh tokens atomically with audit. A subsequent authorized `active=true` requires a new sign-in. An independent governance revocation also locks the account, which SCIM cannot clear. Group membership and role mapping changes revoke affected sessions. Disable a directory to deactivate its managed users and revoke credentials and sessions. Re-enable only after investigating the failure and rotate the credential before resyncing. Unavailable IdP delivery creates no local event until the provisioner retries. Measure actual deprovisioning delay and reconcile the source directory.

The supported subset follows the SCIM core schema and protocol. It provides discovery at `ServiceProviderConfig`, `ResourceTypes`, `Schemas` and `Schemas/{id}` and GET/list/POST/PUT/PATCH/DELETE for `Users` and `Groups`. Lists implement one-based `startIndex`, `count` 0–100, equality on user `userName`, `externalId`, `id` or group `displayName`, `externalId`, `id`, and supported `excludedAttributes`. List pages reflect the current state. Clients can use `If-Match` with returned weak versions for updates. Stale revisions receive 412. Duplicate creates return 409 and clients can re-query before retry. Repeated deactivation, membership operations and deletion preserve authorization outcomes. Omitting `active` or `externalId` on a user replacement preserves the current value. [SCIM core schema](https://www.rfc-editor.org/rfc/rfc7643.html) · [SCIM protocol](https://www.rfc-editor.org/rfc/rfc7644.html)

User fields include `userName` (at most 80 characters), required `emails`, stable optional `externalId`, `active`, `displayName` and `name`. Input `userName` and group display names match without case. SCIM-supplied password, locale, read-only groups/meta and the supported compatibility envelope fields are ignored for authority and secret storage. Application password authentication is disabled for directory-created users. PATCH handles supported scalar/object updates, name subfields, the work-email value path, and group member add/replace/remove by value. Exact boolean strings in Active PATCH are accepted for compatibility. Each group accepts up to 200 direct user IDs owned by that directory, and each user can join up to 200 groups. Unsupported filters, group nesting, bulk, password sync, general attribute projection, custom extensions and arbitrary role claims are outside the supported subset. Deleted resources retain tombstones and uniqueness, so reprovisioning the same identifiers requires operator reconciliation. Reconcile before attempting changes to immutable external identity links.

Refresh/retry guidance: after transient 5xx or expired credentials, inspect the request ID in private logs, confirm tenant transport/auth and audit availability, then re-read current resource state and replay the intended change. Mutations and governance audit share a PostgreSQL transaction. An audit insertion failure rolls back the attempted membership/deactivation and revocation. Rotate by issuing a new credential, verifying provider calls, then revoking the old credential. If compromised, revoke the old one immediately and reconcile all managed accounts and privileged groups.

## Access reviews, compliance and exports

Start an access review from Governance. A campaign captures up to 500 active users or a supplied set of up to 100 active tenant user IDs. It records current local role, account state, directory membership and applicable policy revisions. It does not capture historical effective permissions or OS-level enforcement. A different administrator decides on each administrator's own access. The revision and snapshot are checked before a decision. If entitlements changed, refresh the item and review the new snapshot. A revoke decision disables and locks a subordinate account and revokes its application sessions. Immutable decision rows capture the original evidence and reviewer. Close the campaign when its items are decided. Material changes after the review require a new review or a refreshed item in an open campaign.

Device posture reports enrolled key presence and current server registry states `operator_approved`, `unknown`, `stale`, `noncompliant` or `revoked`. This records operator-assessed posture, without device-management or hardware statements. WireGuard peers are independently managed. Device status data and group/mail directory data require the operator's privacy and retention policies.

Governance downloads one JSON page at a time. The versioned export API accepts `audit`, `changes`, `reviews`, `policy_versions`, `users`, or `devices`. Event windows are at most 31 days and default to the last 30 days. Inventory reflects current state and rejects a historical window. It is paged at up to 500 records. Signed cursors expire after 15 minutes and bind the tenant, dataset, interval and keyset position. Independent pages can reflect later updates or late commits. Use a reviewed database snapshot if an externally consistent point-in-time inventory is required.

The response includes a manifest, scoped rows and `nextCursor`. Each manifest has an export ID, selection, row count and SHA-256 over compact UTF-8 JSON rows with recursively sorted object keys, preserved array ordering and UTC ISO timestamps. Save the receipt and every page. Compare the digest with the logged receipt before using the file as evidence. The app prevents the runtime role from updating or deleting export receipts, administrative changes or review decisions. Privileged database operators retain control over storage. For independent retention, copy receipts and exports to approved access-controlled storage and record chain of custody and retention. The evidence digest verifies contents against a trusted copy or receipt. It is not an external signature.

Audit exports omit source IP addresses. They keep timestamps, actors, targets and request IDs. Directory audit actor IDs identify the provisioning credential without exposing hash or token. Usernames, device labels, review/policy state and organization data can still contain personal or business information. Limit export access, encrypt storage, restrict transfer and apply agreed retention. Record the scope, period, owner, reviewer, exceptions, remediation and recheck for each control. These reports can support a SOC 2 evidence request. They do not replace assessor judgment or prove that controls operated over an entire period.

## Organization lifecycle

Use the owner-scoped `npm run organization --prefix backend -- onboard` with private `MIGRATION_DATABASE_URL`, explicit `ORGANIZATION_ID` (new UUID), `ORGANIZATION_NAME`, `BOOTSTRAP_ADMIN_USERNAME`, `BOOTSTRAP_ADMIN_EMAIL` and `BOOTSTRAP_ADMIN_PASSWORD`. Supply the password through protected environment injection and clear it from the operator environment afterward. The command atomically creates the organization, a dedicated superadmin and an operator audit record. Duplicate organization IDs return a failure without modifying the original. Configure a second verified administrator, test provisioning and SSO, document the network perimeter and assign role owners before onboarding end users.

Offboarding requires the explicit target `ORGANIZATION_ID` and `CONFIRM_ORGANIZATION_OFFBOARD` with the same UUID, then `npm run organization --prefix backend -- offboard`. Export permitted evidence and suspend incoming provisioning and device enrollment before collecting the final inventory. The command atomically disables the organization, accounts, registry devices, provider state and directory credentials, revokes sessions and discards pending OIDC attempts and grants. It returns the affected device IDs to reconcile and revoke at the WireGuard gateway. Apply gateway changes separately and verify them. Disable the upstream app assignments and remove provider configuration/secrets after reconciliation. Records are retained. Repeat calls are idempotent. Review any reactivation or retention cleanup with the operator. [WireGuard operations](NETWORK_PROTECTION.md)

## Optional webhook design

The signing and retry contract is implemented as a small tested helper. Deployment would add an operator-configured destination and transactional outbox. No outbound scheduler or delivery service is enabled. Each event should contain an immutable event ID, tenant, event type, schema version, occurred time and minimal actor/target IDs. Relay only selected governance changes and never include passwords, tokens, endpoint credentials, native traffic or raw device telemetry.

Sign exact UTF-8 bytes with a distinct 32-byte minimum signing secret using HMAC-SHA256 over `<unix-seconds>.<event-id>.<body>`. Send `X-RSX-Event-ID`, `X-RSX-Timestamp`, `X-RSX-Key-ID` and `X-RSX-Signature: v1=<hex>`. Verify in constant time, admit only a five-minute clock window and persist processed event IDs before acknowledging. Key IDs enable overlap for rotation. Use per-tenant operator destination allowlists, TLS verification, redirect rejection, egress/IP admission checks, bounded payload sizes and a five-second deadline.

Persist each attempt and next delivery time in a PostgreSQL outbox, lease work, and acknowledge only a 2xx response. Redeliver the same event ID with a freshly signed timestamp after timeout, 408, 429 or transient 5xx. Use up to eight attempts with jittered exponential backoff from one second, capped at one hour including a bounded `Retry-After`. Keep a dead-letter state, sanitized failure code and administrator retry audit. Treat other 4xx as permanent. Require duplicate-safe receivers and private secret storage. Never claim once-only external delivery.

## Reproduce verification

From the repository root, install lockfile dependencies. Use a disposable PostgreSQL database ending in `_test` with `INTEGRATION_DATABASE_URL` supplied privately. The suites create unique schemas and restricted roles.

```powershell
npm ci --prefix backend
npm ci --prefix admin-dashboard
npm run lint --prefix backend
npm test --prefix backend -- --runInBand --detectOpenHandles
npm run test:integration --prefix backend
node scripts/build-openapi.cjs
node backend/src/validate-openapi.js
npm test --prefix admin-dashboard
Set-Location admin-dashboard
npx playwright install chromium
npm run test:browser
```

On a disposable Linux guest or runner, `sudo bash scripts/test-scim-edge.sh` tests the dedicated TLS listener with a temporary certificate and loopback observer in its own network namespace. PostgreSQL/HTTP tests separately verify the backend's source and provisioning credential checks.
